# Meta conversions: one dataset, three signals

MyDay CRM tells Meta what happened to each lead after the form, so Meta can optimise the lead ads for people who become customers rather than whoever fills in a form.

## The dataset

All events go to **Auto Insurance** (dataset `3253348891512104`), set in `META_CAPI_DATASET_ID`. Staging sets the same variable to **PolicyScanner – Staging Test** (`1703124824536735`), so staging never writes to real data.

From 0123 to 0133 the CRM fanned events out to five datasets (Common, Common Full Funnel, Preferred, Preferred Full Funnel and Auto Insurance). That was retired on 2026-10-24: Meta's Conversion Leads optimisation needs roughly 200 leads a month into **one** dataset with a steady daily flow, and splitting a book this size five ways kept every dataset under that line. The four other datasets still exist in Events Manager but receive nothing.

## The signals

| Signal | Meta event | Queued when | Carries |
|---|---|---|---|
| Lead | `Lead` | a Meta lead arrives (`source = 'meta'`) | contact details |
| Qualified | `CompleteRegistration` | the broker marks the lead qualified | contact + applicant details |
| Sale | `Purchase` | stage Sold, Submitted or Issued, once a premium exists | `value` = **yearly** premium, `currency` = CAD |

- The yearly premium is `premium_history.total_new_premium_annual`, generated by the database from whatever unit the broker typed, so a monthly entry still reaches Meta annualised. It is snapshotted when the sale is queued and never revised: Meta deduplicates on the event id, so a sent event cannot be amended.
- Only Meta leads report anything. Manual, website and TikTok leads queue nothing, at any stage.
- A junk lead is reported by silence: it never gets a `CompleteRegistration`. Meta's model is positive-only.

## How it works

1. **Queue (SQL, same transaction as the change).** `fn_meta_signal_on_lead_created` (trigger on `lead` insert) queues the Lead row. `ensure_conversion_signals(lead_id)` queues Qualified and Purchase; it is called by `set_lead_qualification` (0124) and by `update_lead_stage` on a sale stage (0126). It reads current state and inserts only what is missing, so calling it twice is harmless. Current definitions: **0133**.
2. **Send (Python, every 15 minutes).** `services/meta_signal.py::run_drain_forever` sends Pending rows oldest first to `dataset_id()`. `event_id` is the row id; `event_time` is when the row was queued. Meta rejects `event_time` older than 7 days, which is why the drain runs in minutes.
3. **Failures.** Three attempts, rate limits never count as terminal, and failed rows can be retried from the admin **Meta Conversions** screen. A Purchase without a yearly premium above 0 is failed, never sent.
4. **Duplicates.** The database holds one row per lead and event, and that row's id is the Meta `event_id` on every attempt, so Meta deduplicates a retried request. The send lock is per process, so the backend must run as a single worker; two processes could POST the same row twice and rely on Meta's deduplication.

`meta_signal.dataset_target` is history only: every row since 0133 is `legacy` (Auto Insurance), and the sender, the stuck count and retries only ever handle `legacy` rows. Other labels are from the five-dataset setup: production's 40 August `common` rows went to a different dataset, and staging holds test rows in all five.

## Environment

| Variable | Purpose |
|---|---|
| `META_CAPI_DATASET_ID` | the one dataset events go to |
| `META_CAPI_ACCESS_TOKEN` | system-user token that sends events; unset pauses sending (rows wait as Pending) |
| `META_DATASET_QUALITY_TOKEN` | optional, read-only reporting for the admin screen |

Check an environment from inside the service: `python scripts/check_meta_datasets.py --staging` (or `--production`).

## Meta side

- Lead ads: **Tracking → CRM events → Auto Insurance**.
- Auto Insurance CRM funnel: Lead → CompleteRegistration → Purchase. Optimise on CompleteRegistration; Purchase is too rare to optimise on directly.
